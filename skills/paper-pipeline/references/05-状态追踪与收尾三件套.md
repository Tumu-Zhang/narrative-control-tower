# 05 状态追踪与收尾三件套

## 一、设计原理

叙述性进度文档（"当前进展：第三章已完成大半……"）必然与磁盘实际落位漂移。本管线规定：

> **磁盘实际落位是唯一真相源；状态看板由脚本按磁盘落位生成，叙述文档不再维护进度。**

- 每个小节的状态由其目录内文件**客观推导**：`正文/` 有文件＝已入库；`草稿/`＋`校验/` 都有＝已校核待入库；只有 `草稿/`＝撰写中；约束文件含"待重启"类关键词＝已初始化待重启；否则＝未启动。
- 看板为 CSV，每行一个小节：章、节、目录路径、约束/草稿/校验/正文/图表落位旗标、引用数、状态、阻塞项、最后更新。
- 通用实现见 [scripts/status_board.py](../scripts/status_board.py)（`--check` 只比对 / `--write` 刷新，退出码 0=一致 / 2=有差异或缺失；章节与小节命名正则可用参数适配）。

## 二、开工状态自检

每个窗口开工时、读取任何约束**之前**：

```bash
python status_board.py --root <项目根> --check   # 秒级，只读磁盘与看板比对
```

- 退出码 0 → 直接开工；
- 退出码 2 → 先 `--write` 刷新看板（生成物刷新，不记日志），并核对差异是否提示某小节状态与认知不符。

目的：**保证任何窗口读到的进度状态不早于上一个任务**，防止并发窗口基于过期认知工作。

## 三、收尾三件套

凡产生文件改动的任务（草稿生产、整改、入库、成图、规则落库、约束修订等），收尾前必须完成：

1. **执行日志**：按**任务批次**（非按文件改动）在 `00_项目管理/执行日志.md` 追加一条——日期与事项、窗口角色（生产/校核/整改/约束登记）、改动与产出的文件路径清单、遗留待办。纯阅读、咨询、检索类不记。
2. **状态看板**：`--check` 有差异即 `--write` 刷新（生成物更新，不单独记日志）；`阻塞项` 列的手写文案随状态跃迁一并订正，不得残留过期叙事。
3. **任务约束**：小节状态发生跃迁（如 草稿→校验→正文）时，同步该小节 `任务约束.md` 的当前状态字段。

## 四、执行日志的附加价值：错误史机制

执行日志不只是流水账，它沉淀为**错误史**：

- 每次体检发现、用户批评、覆盖事故都在日志留痕；
- 反复出现的问题升级为**检查项**并赋权重（L1 提醒 → L2 体检必查 → L3 机检断言），同项再犯提高权重；
- 已裁决事项（某口径怎么定、某图怎么画）记入日志后，后续窗口开工先检索历史裁决，**禁止重问已裁决事项**——这是多窗口协作不"失忆、翻烧饼"的关键。

## 五、健康度检查（收工可选）

收工前可运行健康度检查（**只报告不修改**）：扫描目录纯净度（内容树内工程脚本、预建空壳、归档残留、命名违规等），退出码 0=全部通过 / 1=中低风险 / 2=阻断项。检查逻辑与看板共用同一个小节扫描模块，避免两处各自推导而漂移。
