插件与监督工具清单

一、本地 git 仓库
作用：
记录工程每一步变化，方便回退、比较、审查。

什么时候用：
1. 每完成一个阶段提交一次。
2. 每次大改前先看 git status。
3. 审查线程需要对照 git diff 找问题。

常用命令：
git status
git diff
git log --oneline --decorate -n 20
git branch
git add <文件>
git commit -m "说明"

注意：
不要把 API Key、密钥、临时缓存、构建产物提交进仓库。

二、GitHub 远程仓库
作用：
云端备份、PR 审查、issue 追踪、阶段里程碑管理。

什么时候用：
1. 本地阶段提交后推送。
2. 每个阶段开一个 PR 或 draft PR。
3. 审查线程可以围绕 PR 做审查。
4. 问题用 issue 记录。

建议规则：
1. main 分支只放通过验收的版本。
2. develop 或 feature 分支用于开发。
3. 每个阶段用 tag 或 milestone 标记。
4. PR 描述必须包含验收证据。

三、Codex 主开发线程
作用：
真正写代码、跑测试、修 bug、提交。

工作规则：
1. 开始前必须读取工程宪法和阶段验收清单。
2. 不要一次做完整大软件，要按阶段交付。
3. 每个阶段先做可运行骨架，再补功能，再验收。
4. 不能用假数据冒充真实功能。
5. 完成后必须给审查线程足够证据。

四、独立审查线程
作用：
充当外部审查者，专门挑错。

工作规则：
1. 不参与主开发。
2. 不替主开发解释。
3. 按 03-独立审查线程说明.txt 审查。
4. 审查结论必须有证据。
5. 阻断项没修完不能放行。

五、阶段验收清单
作用：
防止工程跳步，防止“差不多完成”。

使用方法：
1. 主开发线程完成阶段后逐项自检。
2. 审查线程逐项复核。
3. 任何阻断项未过，返回主开发线程修复。
4. 通过后再进入下一阶段。

六、可调用的 Codex 能力
GitHub 插件：
用于读取 PR、请求 review、辅助处理 GitHub issue 或 PR 信息。
前提是当前 Codex 环境已经连接 GitHub。

多 agent 工具：
可用于并行审查、架构审查、测试审查。
注意：只有在你明确要求“开一个子 agent 审查某部分”时才使用。

新建 Codex 线程：
可用于创建主开发线程或独立审查线程。
注意：只有你明确要求创建新线程时才调用。

浏览器或桌面自动化工具：
用于启动软件、点击 UI、截图、检查窗口布局。
适合验收 UI、自适应布局、设置页面、权限弹窗。

文件转换工具：
用于资料库能力验证，读取 docx、pdf、txt、md。
后续软件也应内置类似能力或通过受控工具调用。

七、推荐监督节奏
阶段开始：
主开发线程写本阶段计划。

阶段中：
主开发线程随时提交小步变更。

阶段结束：
主开发线程提供构建、启动、截图、日志、文件变化、测试结果。

审查：
独立审查线程按清单给出通过或不通过。

封存：
通过后打 tag 或合并到主分支。

八、最重要的监督问题
每次验收都问：
1. 这个功能是否真的改变了本地文件或真实状态？
2. 是否真的调用了模型、网络、文件读取或权限系统？
3. 用户拒绝时是否真的阻断？
4. 用户确认前是否没有偷偷写入？
5. 重启软件后数据是否仍在？
6. 换一个输入，输出是否真的变化？
7. 有没有日志能证明发生了什么？
