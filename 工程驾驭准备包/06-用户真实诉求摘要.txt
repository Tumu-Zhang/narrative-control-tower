用户真实诉求摘要：叙事中枢 / Narrative Control Tower

一、用户真正想要什么
用户要的不是一个“会写小说的聊天框”，也不是一个“看起来像创作软件的 UI 原型”。
用户真正想要的是一个能长期驾驭长篇小说、剧本、影视化创作工程的 agent 控制系统。

这个系统必须像一个创作总控台：
1. 能管理项目。
2. 能管理人物、剧情、设定、资料、正文、候选稿和废稿。
3. 能让不同模型在权限约束下分工。
4. 能把每一次创作、审核、修改和入库都变成可追踪的工程行为。
5. 能防止长篇创作里最危险的漂移、冲突、遗忘、污染和误入库。

二、用户不是在追求“按钮很多”
用户反感的是空壳式软件：
按钮很多，但点了没有实际作用。
界面很像，但数据没有落盘。
设置能填，但不影响运行。
模型能搜索，但其实是本地硬编码。
资料库能输入文件路径，但根本没有读取文档内容。
章节能生成，但只是套模板，没有真实调用模型。
权限界面存在，但敏感动作没有被拦截。

因此，软件里的每个功能都必须回答一个问题：
它是否真实改变了项目状态、文件、配置、模型调用、权限判断或创作资产？
如果没有，它就不是功能，只是装饰。

三、用户的核心判断标准
用户判断这个软件是否真实可用，不看宣传词，而看这些事：
1. 是否能创建真实本地项目文件夹。
2. 是否能重新打开项目并恢复状态。
3. 是否能配置真实 API Key 并测试连接。
4. 是否能通过运维模型真实检索其他模型。
5. 是否能读取本地文档内容，而不是只读路径字符串。
6. 是否能联网检索作品名、关键词和 URL。
7. 是否能根据输入内容输出不同分析。
8. 是否能让 AI 建议基于用户已填内容，而不是泛泛模板。
9. 是否能先由思考模型生成策略，再由写作模型生成候选稿。
10. 是否能自动审核并暴露风险。
11. 是否能人工确认后才入正文库。
12. 是否能删除稿件并隔离到废稿库。
13. 是否能修改卡片或剧情时生成 ChangeSet。
14. 是否能用权限系统拦截敏感动作。
15. 是否能用日志和文件变化证明发生过什么。

四、运维模型是软件的地基
用户特别强调：软件首先要有运维模型。
运维模型默认只能先接 DeepSeek，目标名称暂定 deepseek-v4-pro。

运维模型不是普通写作模型。
它是软件的底层执行脑，负责：
1. 检索模型。
2. 解释模型能力。
3. 辅助部署其他模型。
4. 调度工具。
5. 分析资料。
6. 规划章节策略。
7. 维护项目治理。
8. 让软件从静态工具变成可执行 agent harness。

如果运维模型没有接通，软件必须承认 agent 能力不可用。
它可以保留离线项目管理能力，但不能假装自己能检索、分析、写作或执行。

五、模型系统的真实逻辑
用户不是要几个固定模型下拉选项。
用户要的是：
用户输入模型名 -> 运维模型联网检索 -> 软件展示候选结果 -> 用户确认 -> 写入配置 -> 用户输入 API Key -> 测试连接 -> 绑定角色。

如果用户输入 kimi，就应该检索 Kimi / Moonshot 相关信息。
如果用户输入 gpt，就应该检索 OpenAI GPT 相关信息。
如果用户输入 mimo，就应该真实检索或明确无法确认，而不是默认匹配 DeepSeek。

模型角色至少包括：
1. 运维模型。
2. 思考模型。
3. 写作模型。
4. 润色模型。
5. 检索/分析模型。
6. 编程/项目修改模型。

可以有懒人模式：
全部角色暂时使用运维模型。
但软件必须明说这是懒人模式，而不是伪装已经部署了多个模型。

六、用户要人类主控，不要 AI 失控
用户不是让 AI 全自动决定一本书。
用户要的是人类作为总导演，AI 作为受控执行团队。

关键规则：
1. AI 可以建议，但用户确认后才能进入控制单。
2. AI 可以生成候选稿，但不能直接入正文库。
3. AI 可以审核，但人工审核是最终门禁。
4. 润色模型只能局部改写，不能偷偷改剧情、设定、人物动机。
5. 删除、入库、改正文、改正典、批量连锁修改必须人工确认。

七、长篇创作的真正痛点
用户要解决的不是“写一章”。
用户要解决的是长篇工程里的连续性治理：
1. 人物会不会漂移。
2. 设定会不会冲突。
3. 伏笔有没有回收。
4. 主线、暗线、副线是否断裂。
5. 改一个人物是否影响旧章节。
6. 候选稿能不能安全入库。
7. 废稿会不会污染上下文。
8. 参考资料会不会造成抄袭或过拟合。
9. 模型会不会绕过控制单胡写。

所以软件必须有创作资产库、依赖图、ChangeSet、事务式入库、废稿隔离和质量门禁。

八、资料库不是摆设
用户说的资料库不是论文资料库，也不是收藏夹。
它可以接收文学作品、影视作品、剧本、表达手法、世界观构造方法、人物关系、节奏结构、本地文件、URL、关键词、作品名。

软件必须真的读取和分析，而不是生成统一模板。
输出必须区分：
1. 软件理解版。
2. 客户审核版。
3. 可学习内容。
4. 不可照搬内容。
5. 抄袭/过拟合风险。
6. 可绑定到哪些章节、卡片、剧情节点或文风控制。

九、UI 的意义是控制工程
用户不是只要漂亮。
用户要的是能控制复杂创作工程的桌面操作台。

UI 必须做到：
1. 母 UI 和子 UI 分清。
2. 状态栏、导航栏、侧栏职责不重复。
3. 设置中心集中管理基础、模型、权限、skills、输出、外观、支持。
4. 主导航只放业务模块。
5. AI 控制台和 skills 管理既然进了设置，就不要再放主导航。
6. 内置 skills 不密集陈列，只提供打开文件夹和恢复基础包入口。
7. 右侧上下文面板必须有真实关系信息。
8. 窗口最大化和缩小时布局都合理。
9. 可点击控件必须有反馈或实际结果。
10. 不可用功能必须明确禁用或说明原因。

十、为什么前一个版本不满足用户
前一个版本的问题不只是 UI 小瑕疵。
根本问题是：它被做成了“可运行原型”，而不是“可执行 agent 工程系统”。

它让用户失望的原因包括：
1. 模型检索像本地匹配。
2. 资料库像套模板。
3. 章节生产不像真实模型调用。
4. 设置保存没有实际影响。
5. skills 陈列但不可理解。
6. 项目创建不像真实工程文件夹。
7. UI 结构和响应式布局不成熟。
8. 权限、模型、资料、生产、入库之间没有形成真实执行链。

新工程必须把这些作为反面清单。

十一、给 Codex 的行为要求
Codex 必须把自己当成工程执行者，而不是 UI 生成器。

开工时必须：
1. 先建立工程纪律。
2. 再设计 agent harness。
3. 再做项目文件系统。
4. 再做运维模型和权限系统。
5. 再做资料库和章节生产。
6. 最后再完善 UI。

每个阶段必须：
1. 有构建结果。
2. 有运行结果。
3. 有截图。
4. 有日志。
5. 有文件变化。
6. 有测试或手工验收证据。

没有证据，不要说完成。

十二、一句话总结
用户要的是：
以运维模型为底座、以权限系统为边界、以本地项目文件为真实载体、以创作资产和连锁修改为核心、以人类确认为最终门禁的长篇叙事 agent 控制塔。

任何偏离这个目标的实现，无论 UI 多完整，都不是用户想要的软件。
